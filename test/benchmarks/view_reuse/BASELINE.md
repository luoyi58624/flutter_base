# 2026-11-12 基线分析

本轮只新增测试与报告，没有优化 ElView、ElListenableBuilder 或 recycler。生产基线为 `ffed199d6eb0c7aeacf2a9f0ea4bc405f0b5d770`，Flutter 3.47.5 / Dart 3.13.4，Windows 无头 debug，单进程、BelowNormal 优先级。

短样本 60 项测试通过；计时模式 100 项测试通过，132 个测量场景各两轮，共 264 组结果、3,168 个测量样本。定向静态分析无问题。另有两项独立行为观察报告了当前实现的语义缺口，见文末。

完整数据与源文件指纹见 [baseline-2026-11-12.jsonl](baseline-2026-11-12.jsonl)，测试结构、运行方式和指标定义见 [README.md](README.md)。下表工作次数均为**一轮 12 次操作的累计**，两轮确定性计数一致；时间为每次操作的中位数，按“第 0 轮 / 第 1 轮”保留。

## ElView：保留对象之后仍然做了什么

24 个文本节点，普通重建时均保留 Element 和 RenderObject。

| 操作 | ElView 配置更新 | 文本环境构建 | ElView 布局 | 级联 |
| --- | ---: | ---: | ---: | ---: |
| 同样参数，创建新 ElView 配置 | 288 | 288 | 0 | 0 |
| 等值新字符串、等值新样式 | 288 | 288 | 0 | 0 |
| 普通 Widget 更新并改变文字 | 288 | 288 | 288 | 0 |
| 固定 ElView，等值文字通知 | 0 | 0 | 0 | 0 |
| 固定 ElView，变化文字通知 | 0 | 0 | 288 | 0 |

普通重建已经避免无意义的文字布局和样式级联，但仍然更新文本环境。这给后续优化提供了具体观测点。固定文本通道已经省掉配置与环境更新；文字真变时的布局仍然发生，不能以跳过实际排版作为优化目标。

“原生通知文字”是 ValueListenableBuilder + RichText；普通文本是 SizedBox + RichText。装饰负载包含圆角、背景、内边距与点击，原生由多个节点组合。这里没有一个实现对所有负载都占优；尤其创建数据不能替代重建数据。不同测试操作的范围也不同，不能拿“普通重建”和“通知直达”直接相除，宣称内核固定加速多少倍。

## ElListenableBuilder：等值数据能否完全不重建

24 个叶子，每次都真正发送通知：

| 接法 / 操作 | 监听器 Element 构建 | 业务 builder | ElView 配置更新 | 布局 |
| --- | ---: | ---: | ---: | ---: |
| ValueListenableBuilder / 等值 | 288 | 288 | 288 | 0 |
| ElListenableBuilder 无 select / 等值 | 288 | 288 | 288 | 0 |
| ElListenableBuilder 标量 select / 等值 | 288 | 0 | 0 | 0 |
| ElListenableBuilder record select / 等值 | 288 | 0 | 0 | 0 |
| ElListenableBuilder 返回新 List / 等值 | 288 | 288 | 288 | 0 |
| ElListenableBuilder 新 List + 值比较 / 等值 | 288 | 0 | 0 | 0 |
| 标量 select / 选中字段变化 | 288 | 288 | 288 | 288 |
| 标量 select / 无关字段变化 | 288 | 0 | 0 | 0 |
| 标量 select / 同帧变化再回原值 | 288 | 0 | 0 | 0 |

当前答案是：**能完全挡住等值通知引发的业务子树更新，不能完全挡住自身 Element 重建。** 筛选发生在 build 阶段；通知已经标脏，并在 recycler 中触发对应构建作用域的处理。

默认比较使用所选值的相等语义。每次新建普通 List 不会自动进行内容比较；record 或明确的 `shouldRebuild` 可以表达展示字段相等。自定义谓词允许等值时要求重建，因此未来不能无条件在它之前加一层默认相等拦截。

静态内容放进 child 后，12 次选中字段变化的静态 Widget 创建和 build 均为 0；放在 builder 内则各有 288 次。动态叶子的 288 次更新仍然存在，这两类收益应分别讨论。

## SliverList 与 recycler：稳定容器、相同展示数据

视口与缓存中有 9 个条目，每卡三个 ElView。数据等值通知 12 次：

| 接法 | 卡片构建 | ElView 配置更新 | 文本环境构建 | select Element 构建 | 中位 µs |
| --- | ---: | ---: | ---: | ---: | ---: |
| SliverList + 整卡 ValueListenableBuilder | 108 | 324 | 216 | 0 | 2256 / 444 |
| recycler + 整卡 ValueListenableBuilder | 108 | 324 | 216 | 0 | 2740 / 721 |
| recycler + 整卡 select | 0 | 0 | 0 | 108 | 970 / 417 |
| recycler + 标题局部 select | 0 | 0 | 0 | 108 | 729 / 455 |
| recycler + ElView 文本直达 | 0 | 0 | 0 | 0 | 69 / 47 |

这些场景的 ElView 布局与级联均为 0。静止状态的数据通知下，换成 recycler 并不会自动减少整卡重建；筛选粒度才决定能省掉哪些更新。直达文本仍然执行 108 次绑定通知，只是没有因此进入 Widget 重建与布局。

只改变一个可见标题时：

| recycler 接法 | 卡片构建 | ElView 配置更新 | 文本环境构建 | ElView 布局 |
| --- | ---: | ---: | ---: | ---: |
| 整卡 ValueListenableBuilder | 108 | 324 | 216 | 24 |
| 整卡 select | 12 | 36 | 24 | 24 |
| 标题局部 select | 0 | 12 | 12 | 24 |
| 文本直达 | 0 | 0 | 0 | 24 |

一次文字变化引起标题和外壳各一次布局；四种接法均确实呈现新文字。全局数据源通知所有槽位，未变化条目的 select 仍会执行，局部筛选不是订阅端完全无工作。

## 滚动换绑：相同与不同展示数据分开看

相同展示数据，12 步向前滚动覆盖 14 次进入窗口的记录：

| 接法 | 新槽位 | 换绑 | ElView 配置更新 | 文本环境构建 | ElView 布局 | 中位 µs |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| SliverList | 14 | 0 | 0 | 28 | 42 | 4474 / 2283 |
| recycler + 整卡普通监听 | 0 | 14 | 42 | 28 | 0 | 2951 / 828 |
| recycler + 整卡 select | 0 | 14 | 0 | 0 | 0 | 1697 / 787 |
| recycler + 局部 select | 0 | 14 | 0 | 0 | 0 | 1341 / 811 |
| recycler + 文本直达 | 0 | 14 | 0 | 0 | 0 | 1336 / 831 |

SliverList 的“配置更新为零”来自新建节点，绝不表示没有工作。recycler 的四种接法都保留槽位，而普通监听仍更新卡片。select 把这些配置更新挡住，但自身有 14 次 Element 构建。文本直达也不能消除滚动容器、IndexedSemantics 等包装器的必要工作，因此不应描述成“整个列表滚动零重建”。

不同展示数据、自然高度场景，12 步发生 13 次新建或换绑：

| 接法 | 新槽位 | ElView 配置更新 | 文本环境构建 | ElView 布局 | 中位 µs |
| --- | ---: | ---: | ---: | ---: | ---: |
| SliverList | 13 | 0 | 26 | 39 | 2364 / 1539 |
| recycler + 整卡普通监听 | 0 | 39 | 26 | 26 | 1613 / 1695 |
| recycler + 整卡 select | 0 | 39 | 26 | 26 | 1523 / 1455 |
| recycler + 局部 select | 0 | 13 | 13 | 26 | 1815 / 1135 |
| recycler + 文本直达 | 0 | 0 | 0 | 26 | 1326 / 1061 |

每次标题都变化时，整卡 select 无法省掉卡片更新，还增加比较；细分消费点才能保留静态部分。这里两轮时间并不始终按工作量排序，不能据单轮中位数宣布某方案必然更快。

## ElListenableBuilder 放在整张列表外面

使用不同文字数据，缓存窗口中 8 条；条目内部统一采用文本直达。12 次等值新列表通知：

| recycler 外层接法 | 列表 builder | itemBuilder | ElView 配置更新 | 文本环境构建 | 外层监听 Element 构建 | 中位 µs |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| ValueListenableBuilder，每次刷新列表配置 | 12 | 96 | 288 | 192 | 12 | 1673 / 1278 |
| ElListenableBuilder + ListEquality | 0 | 0 | 0 | 0 | 12 | 205 / 170 |

两者槽位挂载、ElView Element/RenderObject 新建及卸载均为零；普通父刷新仍创建 288 份 ElView Widget 配置。外层 select 确实挡住父配置刷新带来的整树更新，但仍有一次自身构建和 500 项数据比较。稳定列表本来就不重建时，额外套一个监听器不自动产生这些收益；本表专门比较父配置刷新路径。

## 独立语义观察与后续目标边界

两个观察都复现了旧内容保留，并在 JSONL 中以 `semantic_gap: true` 记录：

1. 选择值不变时，父级将 builder 和 child 从 before 换成 after，界面仍显示 before。
2. 选择值不变时，builder 依赖的 Inherited 配置从 before 换成 after，界面仍显示 before。

这不是有效的性能优化。本轮没有修改实现，也没有把该行为写成应长期维持的通过条件；不能把“100 项基准测试通过”理解成上述语义正确。

下一步定目标时已有三组可独立验收的指标：ElView 普通重建的文本环境工作；ElListenableBuilder 等值通知的自身调度；复杂条目从整卡更新缩小到字段更新。还需要先明确父配置、继承环境、自定义谓词与同帧合并的语义边界，再选择实现方式。

时间限制：这些是带探针的无头 debug 墙钟，初轮与后轮明显受 JIT/调度影响；仅用于本地后续同场景对照。未测设备帧率、GPU、图片、内存峰值与长期 GC，不提供泛化的加速倍数。
