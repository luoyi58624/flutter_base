# ElView 事件与元素常驻开销基准

本目录量 ElView 自身的固定成本：挂载、配置更新、指针派发和每个视图的常驻内存。重建与回收复用的基准在 [view_reuse](../view_reuse/README.md)，两者互不替代。

## 运行

默认只用很小的规模检查场景能跑通，不计时、不测内存：

```powershell
flutter test test/benchmarks/view_event --no-pub --concurrency=1 --timeout 60s
```

计时与内存需要显式开启，内存测量要同时打开 VM 服务。单次约 1.5 分钟，占用一个核，建议降低优先级：

```powershell
$taskProcess = [Diagnostics.Process]::GetCurrentProcess()
$taskProcess.PriorityClass = 'BelowNormal'
flutter test test/benchmarks/view_event --no-pub --concurrency=1 --timeout 180s --enable-vmservice --dart-define=VIEW_EVENT_TIMING=true --dart-define=VIEW_EVENT_MEMORY=true
```

输出中 `VIEW_EVENT_RESULT ` 后面是 JSON。不要为验证启动前台应用，也不要批量重复跑。

## 场景

| 场景 | 负载 | 计时范围 |
| --- | --- | --- |
| `mount_*` | 2000 个 4×4 的 ElView 放进 Wrap | 一次 `pumpWidget`：构建、挂载、布局、绘制 |
| `update_*` | 同一棵树换一批新的声明与样式值 | 一次 `pumpWidget`：配置更新到绘制 |
| `tap_chain` | 16 层嵌套、每层声明 `onTap` | 300 次按下加抬起 |
| `move_on_tap_route` | 同上 | 按住后 300 次容差内移动 |
| `move_on_drag_route` | 最内层声明拖拽，其余 15 层声明点击 | 按住后 300 次移动，拖拽已开始 |
| `retained_*` | 20000 个 ElView | 挂载前后各做一次完整回收后的堆差，按类拆分 |

`*` 取三种声明：`plain` 只有样式，`tap` 多一个 `onTap`，`focus` 多一个 `onFocus` 样式变体。

## 口径

- 运行环境是 `flutter test` 的调试模式（JIT、断言开启），不是真机发布模式。绝对耗时不代表线上，只用于同一台机器上相邻提交的对比。
- 计时每个场景热身 4 次、采样 15 次，报告中位数与最小值。机器同时在用时单次波动可达数倍，小于波动的差异不下结论。
- 内存读的是 VM 分配概况里回收之后的存活字节，按类给出每个视图的增量，结果是确定的。字节数对应未压缩指针的 64 位桌面；移动端 64 位使用压缩指针，对象字段占用约为一半。
- `retained_*` 的总量包含声明、样式、语义配置等所有随视图存活的对象，不只是 Element 和渲染对象。

### 常驻内存

每个视图的存活字节，64 位桌面。结果是确定的，两次读数一致。

| 对象 | 改动前 | 改动后 | 来源 |
| --- | ---: | ---: | --- |
| `ViewElement` | 320 | 208 | 焦点对象：元素少 14 个字段 |
| `ElRenderView` | 672 | 640 | 宿主接口：渲染对象少 4 个字段 |
| 每视图闭包，纯样式 | 96 | 0 | 宿主接口：不再为每个视图分配两个闭包 |
| 每视图闭包，可点击 | 288 | 192 | 同上 |
| 每视图闭包，带焦点变体 | 480 | 288 | 同上，另少两个焦点回调 |
| `_ViewFocus`，仅带焦点来源的视图 | 0 | 144 | 焦点对象：状态从元素搬到按需对象 |
| `EventDispatcher` | 144 | 160 | 回调位图：多两个字段 |

| 声明 | `ad6359f` | `9534c23` | 差 |
| --- | ---: | ---: | ---: |
| 纯样式 | 6326 | 6042 | −284（−4.5%） |
| 可点击 | 7066 | 6831 | −235（−3.3%） |
| 带焦点变体 | 9991 | 9770 | −221（−2.2%） |

总量来自调试模式，含调试专用对象，百分比偏保守；各类的字节差与模式无关。回调位图那次提交曾让可点击视图多出 124 字节，随后的 `b835c85` 复用声明位图后收回，净增只剩分发器上的 16 字节。

测量时机器在正常使用，同一提交两轮之间就能差出三成（第二轮的 `9a07d8d`、`ba6b139` 明显偏高）。只把两轮方向一致的差异当作结论：

| 改动 | 两轮一致的变化 | 无法下结论 |
| --- | --- | --- |
| 回调位图 | 可点击视图更新快 10%–35%；点击派发快 18%–26%；点击路线上的移动快 10%–22% | 挂载 |
| 路线拆分 | 点击派发快约 8%；点击路线上的移动快 11%–24%；拖拽路线上的移动快 10%–17% | 挂载、更新 |
| 焦点对象 | 无 | 全部场景，两轮方向相反 |
| 宿主接口 | 无 | 全部场景，差异在波动之内 |
| 松手核对 | 无 | 点击派发最小值高 4%，单轮、在波动之内 |

首尾对比（`ad6359f` → `9534c23`）：可点击视图更新快 21%–30%，点击派发快 11%–17%，点击路线上的移动快 18%–21%；纯样式视图的挂载与更新、拖拽路线上的移动没有可分辨的变化。

焦点对象和宿主接口两项的收益在内存，不在耗时：每次挂载省下的两次闭包分配和几次空调用，在这个精度下量不出来。
