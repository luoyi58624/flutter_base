# RecyclerView 首轮真机性能记录

日期：2026-11-05。

本轮相同按钮文档内容的快速滑动对照中，Dart RecyclerView 的 UI 帧耗时 P95 和较长的帧生产间隔减少；尖峰仍然存在。UI 最大耗时略高，raster P95 也没有改善。这组数据支持继续验证结构复用的效果，不能证明已经达到原生流畅度或根治滚动卡顿。

## 环境与操作

| 项目 | 本轮设置 |
| --- | --- |
| 设备 | PLJ110，Android 17 |
| Flutter | 3.47.5，Profile |
| 渲染 | Impeller / Vulkan |
| 页面 | 实际 Button 文档，11 种示例小节各重复 100 次，另加页首，共 1101 项 |
| 基线 | 原文档滚动容器，keepAlive 为 false |
| 对照 | 本目录实现的 Dart RecyclerView，使用相同文档视图 |
| 计帧 | 导航后等待 800ms 开始，采样窗口 12 秒 |
| 快速手势 | 6 次，每次 100ms；先正向 3 次，再反向 3 次 |
| 手势坐标 | x=620，y=2300 → 650；反向为 y=650 → 2300 |

两种容器使用相同坐标、持续时间和内容。脚本在每次输入前检查目标示例是否仍在前台；ADB 注入的手势可以统一两次操作，但不能代替真实手指的触摸延迟测量。

这一轮按基线、RecyclerView 的顺序各测一次，没有进行多轮交叉或随机顺序采样。首屏初始化和导航过渡不在计帧窗口内，因此不是冷启动首次挂载测试。

## FrameTiming 结果

单位为毫秒；超过 8.333ms 的数量使用采样代码中的 `>8333μs` 判断。

| 指标 | 原滚动容器 | Dart RecyclerView |
| --- | ---: | ---: |
| 记录帧数 | 671 | 685 |
| UI P50 | 0.764 | 0.816 |
| UI P95 | 4.141 | 1.674 |
| UI 最大值 | 17.349 | 18.706 |
| UI 超过 8.333ms | 20 / 671 | 6 / 685 |
| Raster P50 | 2.524 | 2.279 |
| Raster P95 | 5.014 | 5.454 |
| Raster 最大值 | 11.157 | 8.571 |
| Raster 超过 8.333ms | 3 / 671 | 3 / 685 |

UI 指标来自 `FrameTiming.buildDuration`，表示 UI 线程的帧阶段耗时，不能当成某个条目 `Widget.build` 函数的独立耗时。raster 指标来自对应的光栅阶段。两者处于流水线的不同阶段，不应简单相加后作为用户看到的帧间隔。

本轮 UI P95 从 4.141ms 变为 1.674ms，超过 8.333ms 的 UI 样本从 20 个变为 6 个，说明该样本中较重的 UI 帧减少。同时，UI 最大值从 17.349ms 变为 18.706ms，raster P95 从 5.014ms 变为 5.454ms；没有证据表明全部阶段或最坏情况都得到改善。

## 帧生产间隔

将记录帧的 vsync-start 时间排序后，计算相邻时间差，仅保留 `0 < gap < 100ms` 的样本，以排除较长的空闲段。

| 指标 | 原滚动容器 | Dart RecyclerView |
| --- | ---: | ---: |
| 有效间隔样本 | 669 | 684 |
| 间隔 P50 | 8.278ms | 8.279ms |
| 间隔 P95 | 16.556ms | 8.284ms |
| 超过 12.5ms 的间隔 | 77 / 669 | 30 / 684 |

这反映的是 Flutter 已生产帧所关联的 vsync-start 节奏，**不是 SurfaceFlinger 的实际呈现时间**。过滤长空闲段也不能排除全部短暂停顿；这里的较长间隔数量不能直接称为系统掉帧数。此次未测得完整的输入到实际呈现延迟，也没有通过这些数值证明画面已经始终按 120Hz 呈现。

## 可以与不可以得出的结论

- 本次重复模板文档中，UI P95、较重 UI 帧数量和较长帧生产间隔均有可见差异。
- 尖峰仍在，UI 最大值略变差；raster P95 没有改善，超过 8.333ms 的 raster 样本数量相同。
- 两边都使用有限种真实文档模板与相同视图，重复 100 次的场景有利于检验跨数据项的结构复用；不能推导原本只有 11 个各不相同小节的页面，在首轮进入时也会获得同等改善。
- 单组有限样本无法排除顺序、热身、系统调度等因素，也不能推广到任意 Widget、不同数据分布或持续的 20ms 同步工作。
- 本轮没有修改 Flutter 引擎，没有测量 Android 原生列表的同期结果，不能据此声称原生般流畅、全部卡顿已经解决或问题只来自某一个调度环节。
