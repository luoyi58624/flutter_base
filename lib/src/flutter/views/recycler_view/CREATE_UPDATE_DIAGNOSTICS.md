# 创建、更新与缓存阶段诊断

日期：2026-11-06。起点提交 `29f8cab`，本轮新增实际成本和身份测试，并修复隐藏图层的多余绘制。无头、串行、BelowNormal 优先级，每项 90 秒超时；没有操作手机或用户正在运行的应用。

## 结论

本次测到的同类型场景确实保留 Element、State 和 RenderObject 更新数据，没有退化成整棵销毁重建。复杂内容仍需更新叶子、排版变化的文字并记录绘制，保留结构不代表后续工作为零。

同时发现并修复一个实际浪费：刚离屏的旧 holder 被拿来预取新记录时，旧 OffsetLayer 尚 attached，Flutter 的独立边界绘制会先把隐藏内容画一次。相同反例中的两次隐藏正文绘制已降为零。

全部逐次数据、阶段事件和修改前后隐藏绘制结果见 [CREATE_UPDATE_DIAGNOSTICS.json](CREATE_UPDATE_DIAGNOSTICS.json)。日志位于本机 `.codex-run/recycler-create-update-20261106/`。

## 真实复杂卡片：创建与更新各需要多少时间

使用示例 RecyclerCardsPage 的真实 Adapter、ViewHolder 和完整行，不是只返回一个空 holder。每张卡片含 195 个 Element、16 个 State、121 个 RenderObject，包括离线照片、阴影、裁剪、渐变、多段文字、图标、统计和进度。

同一个宿主提供两个固定、可见、独立重绘的槽位：一个 holder 始终挂载后跨记录换绑，另一个每次真正创建再卸载。每轮交替先创建或先更新，预热 4 轮后测量 12 轮；照片提前解码，树遍历和身份断言放在计时区间外。

单位为 ms，表内是本次进程的 P50 / P95：

| 操作 | 照片类型 0 | 照片类型 1 |
| --- | ---: | ---: |
| 创建根 Widget 描述的回调 | 0.019 / 0.025 | 0.021 / 0.024 |
| 首次模型绑定回调，尚未挂载 | 0.012 / 0.015 | 0.012 / 0.015 |
| 完整创建、绑定、挂载并完成一次 pump | 15.485 / 19.671 | 14.462 / 18.465 |
| 已挂载 holder 的模型换绑回调 | 0.060 / 0.089 | 0.065 / 0.084 |
| 保留结构换绑并完成一次 pump | 4.773 / 8.093 | 4.583 / 7.270 |
| 单独卸载并完成一次 pump | 2.465 / 3.060 | 2.289 / 3.806 |

创建回调只构造根 Widget 配置，子孙实际创建、挂载、构建、布局和 CPU 绘制记录发生在完整 pump 中。不能拿 0.02ms 的回调代替约 15ms 的完整挂载成本。首次绑定还没有挂载监听者，不能直接用它与已挂载换绑回调比较业务复杂度。

换绑的每一次操作均断言：195 个 Element、16 个 State、121 个 RenderObject 全部保持原身份；新增、移除各为 0，State 始终 mounted，RenderObject 未 disposed。每种类型的 12 个测量记录 ID 都不同，标题确实改变。

创建正对照每轮都挂出独立的新树，卸载后逐个验证 Element 已卸载、State 已销毁、RenderObject 已 disposed。因此“零销毁”不是一个从未能检测到销毁的空计数器。

这些数字是 Debug JIT 测试进程墙钟，包含 Flutter 测试框架与 CPU 绘制记录，不含真实 GPU 光栅和手机中文字形环境。样本少，P95 可能落在最大样本；不据此宣称 Android 帧耗时或版本提升百分比。

## 真实 RecyclerView 是否持续销毁重建

另外制作了一张带 9 个动态消费点的复杂卡片，包含 174 个 Element、10 个 State、128 个 RenderObject。先在单独宿主比较保留结构更新与变化 Key 的强制销毁重建，再放进真正的 RecyclerView 快速跨越多屏往返。

真列表共 10,000 条记录、2 种重复类型，首屏 2 个 holder，位置缓存为 0、预取关闭、每种类型池容量为 1。初始挂载后进行 4 次预热和 24 次测量位移，每次位移 6 个条目高度，测量覆盖前后两个方向。

| 观察项 | 结果 |
| --- | --- |
| 首屏 holder | 2 |
| 首屏后新增 holder / 根 Widget 描述 | 0 / 0 |
| 首屏后行 State 初始化 / 销毁 | 0 / 0 |
| 每个 holder 累计绑定的不同记录 ID | 17 |
| 跨 ID 的 Element / State / RenderObject 更替 | 全部 0 |
| 固定卡片根 build | 0 |
| 每个换绑卡片的动态消费点 build | 9 |

本次最终核心进程中，单卡更新 pump P50 为 7.557ms，强制销毁重挂为 19.320ms；保持模型不变的空 pump 校准为 0.231ms。它们是带探针的另一套夹具，不能与上面的真实卡片进程互换，也不能机械扣掉空 pump 得到“净成本”。

每个测试分别计根和动态叶子的布局、绘制记录时间。外层根 layout 为 0 不代表子孙没有排版：本次保留结构更新的动态叶子根 layout 合计 P50 为 1.569ms；其根回调与叶子回调可能嵌套，不能相加作为整帧总耗时。

在保留的 Element 上替换不可变 Widget 描述是 Flutter 的正常更新路径，不等于新增 Element。本测试同时打印描述变化、根描述工厂调用与 Element/State/RenderObject 身份，避免混为一谈。

## 现在的 cache 到底做了什么

现有默认设置是位置缓存 2 项，另沿当前滚动方向预取 2 项。缓存按条目数量配置，尚没有按像素距离设置上下缓冲区域的参数。回收池则按类型保留可换绑结构，是另一层机制。

预取在当前可见布局完成后，按剩余预算执行，并不自动生成一个独立准备帧。预取赶在条目进入屏幕之前完成时，确实可以分开布局与绘制：

| 同一记录的工作 | 屏外准备帧 | 随后进入屏幕的帧 |
| --- | ---: | ---: |
| 挂载 | 1 | 0 |
| 数据构建 | 1 | 0 |
| 真实 RenderParagraph 排版 | 1 | 0 |
| 正文绘制 / 段落绘制 | 0 / 0 | 1 / 1 |
| 再次绑定 | — | 0 |

holder、Element 和 RenderObject 保持同一对象。这里直接统计真实 RenderParagraph.performLayout，避免用外层 RenderProxyBox 的零 layout 错误推断文字没有排版。

关闭预取或零预算的对照中，新记录在进入帧绑定、段落排版、绘制。一次跨越两项预取范围、跳到记录 8–11 后，新增 holder 仍为 0，但该进入帧需要 4 次换绑、4 次段落排版、4 次正文绘制。**这说明回收成功与工作是否已经提前完成是两件事。**

当前同步绑定成本样本还存在覆盖边界：根布局缓存命中时，独立段落边界可能在后续全局 flushLayout 中排版，晚于同步样本结束。本夹具的 attach 回调只作记录，没有修改文本，能排除 attach 自己更新数据的干扰；但这只能证明有未计入同步样本的布局工作，不能单凭一次计数认定预算超时，更不能把它判为手机变慢的根因。隐藏预取分支的实际低估毫秒数仍需单独量化。

## 本轮修复：隐藏项为什么仍会 paint

原来只在 viewport.paint 中检查 visible。Flutter 的 PipelineOwner.flushPaint 会先独立处理更深的脏 RepaintBoundary；刚退出屏幕的边界，其旧图层在父视口重新绘制前仍 attached，所以隐藏换绑也会被画。

复现条件：项高 100、视口高 400，类型按每 4 项交替，位置缓存 1 项、预取 2 项并提供充足准备预算。首屏 0–3 已绘制，滚到 4–7 时，旧 holder 被复用于屏外记录 8、9。

- 修复前：记录 8、9 各发生一次隐藏正文绘制，合计 2 次，Element 没有重建。
- 修复后：隐藏正文和段落绘制均为 0。继续滚动让 8、9 真正进入视口后，原 Element 正常绘制正确的新文字。

修复仅在内部逐项重绘边界隐藏时调用 layer.remove()，递归摘下 Layer 子树；Element、RenderObject 与已有绘制缓存均保留。没有释放图层，没有给显隐无条件 markNeedsPaint。

补充两项回归均通过：静态同位置缓存返回时复用同一个 OffsetLayer，绑定、布局、正文绘制全部为 0；嵌套 RepaintBoundary 隐藏期间更新文本不绘制，返回后保留原图层并实际画出最新文字。

这消除了一个已复现的浪费路径，没有把按项数缓存扩展为像素区域，也没有证明手机整体卡顿已经解决。
