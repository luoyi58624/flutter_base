# 外卖示例的结构复用与滚动开销

2026-11-06，Windows，Flutter 3.47.5 / Dart 3.13.4。测试使用无头 `flutter_test` Debug，390×900、DPR 1，沿用测试默认字体，未加载生产中文字体。下文耗时为主机 `Stopwatch` 包围真实绑定和 `pump` 的墙钟时间，包含测试框架、Debug 检查和调度，**不等于目标设备的 Profile UI / Raster 帧耗时**。

## 复现与原因

旧版取自 `1f3d3cf` 已提交的三个外卖源码文件，其余滚动和文字内核使用当前工作树。前后对照期间核对了内核文件哈希，内容没有变化。

旧实现有三项可重复观察的开销：

- 整张商家卡片监听记录，每次换绑都会重新生成卡片、布局、标签、按钮与文字样式。
- 菜单和内部 ListView 的 Key 跟随商家 ID，导致横向滚动容器、餐品卡片、图片和按钮随换绑重新挂载。
- 内层沿用默认 250px 缓存范围，每家店会额外挂载多道横向不可见的餐品。

新实现保留商家与餐品的 `ElCard`，品牌组件决定卡片底色。商家文案与图片在消费叶子更新；样式和相同文案实例保留。横向滚动宿主与餐品槽位继续复用，换店时停止旧活动，显式恢复新店的菜单位置。菜单尺寸、餐品数量与滚动行为相同时，菜单外框也保留原 Widget。

餐品本来就采用固定宽度，因此内层通过 `itemExtentBuilder` 返回已知的「餐品宽度 + 6px」，缓存范围设为 0；商家外层仍按实际内容测量高度。尺寸回调随餐品数量改变，让官方布局刷新滚动范围，避免保留节点后从 10 道变成 12 道时暂时沿用旧范围。每店依然有 10–12 道餐品，字号、可见内容、随机图片和横向操作保留。

## 同一实际卡片换绑

保持真实页面及其数据模型存活，通过其 Adapter 创建并挂载实际 holder，再连续绑定 12 个不同商家 ID：24、48……288。它们菜系与餐品数量一致，排除必要的结构差异。每次均验证店名和图片 URL 确实切换到新 ID。

| 工作量，12 次合计 | 旧版 | 修改后 |
| --- | ---: | ---: |
| 断网占位场景，新建 / 移除 Element | 7992 / 7992 | 0 / 0 |
| 已解码图片场景，新建 / 移除 Element | 7488 / 7488 | 0 / 0 |
| 新建 / 移除卡片、布局、按钮及滚动框架节点 | 432 / 432 | 0 / 0 |
| 既有框架 Widget 更新 | 180 | 0 |
| 保留相同横向 Scrollable State 的次数 | 0 | 12 |
| 初始单卡 Element 数，断网占位场景 | 768 | 470 |

图片成功场景使用可控的 256×256 PNG，通过真正的 `Image.network`、`ResizeImage` 与解码缓存加载；每个商家和餐品保持不同 URL / 缓存键。解码在计时前完成，窗口内验证没有新增请求、实际 `RawImage.image` 非空。它覆盖缓存命中路径，不包含首次下载、冷解码或真实照片的 GPU 开销。

下面是一次有界前后对照的 P50 / P95，单位 ms。12 次记录丢弃前 2 次预热，百分位采用 nearest-rank；样本量有限，不能当作稳定设备指标。

| 场景 | 旧 P50 / P95 | 新 P50 / P95 |
| --- | ---: | ---: |
| 单卡换绑，断网占位 | 71.915 / 88.402 | 15.886 / 21.734 |
| 单卡换绑，图片缓存命中 | 57.625 / 83.506 | 12.278 / 15.213 |
| 断网占位，仅 Adapter 绑定阶段 | 0.288 / 0.783 | 0.271 / 0.315 |
| 断网占位，卡片布局子树 | 48.255 / 63.419 | 2.928 / 6.041 |

卡片布局测量包含其布局期间触发的内层菜单构建，不能解释成纯文字排版耗时。绑定阶段都不足 1ms；主要减少的是后续挂载和布局工作。

## 实际页面快速滚动

另一项测试直接滚动完整外卖页面，保留变高商家、不同菜系、10–12 道餐品、默认外层回收配置与真实购物车；使用默认拒绝网络的同一占位场景，每帧纵向跳转 480px，连续 12 帧，再每帧移动 1px 测 12 帧。

| 工作量或墙钟，快速滚动 12 帧 | 旧版 | 修改后 |
| --- | ---: | ---: |
| 新建 / 移除 Element | 10766 / 9990 | 478 / 0 |
| 末帧仍挂载的 Element | 2349 | 1455 |
| P50 | 69.136ms | 18.135ms |
| P95 / 最大值 | 149.922ms | 25.908ms |

本次快速滚动 P50 约降 73.8%，耗时约为原来的 1/3.8。478 个新节点包含首次需要的新 holder，不能和同一 holder 的无谓重建混为一谈。

后续每帧 1px 移动时，前后都没有节点增删，P50 为 4.698 → 3.181ms；这条路径本来就没有大量重新挂载，不能将快滚场景的改善倍数套用过来。

## 回归与验收边界

功能测试覆盖三种外层容器、横向与纵向独立滚动、换绑后的餐品加入购物车、商家菜单位置往返、惯性中换绑、长菜单经过短菜单复用、筛选、暗色与窄屏大字。性能测试用节点和框架复用作为回归断言，不设置依赖机器速度的毫秒通过门槛。

```powershell
# 在 example 目录运行，仅执行外卖相关的有界无头测试。
flutter test test/recycler_takeaway_test.dart test/recycler_takeaway_performance_test.dart --no-pub --concurrency=1 --timeout 60s
```

`TAKEAWAY_BIND_WORK`、`TAKEAWAY_FAST_SCROLL`、`TAKEAWAY_SMALL_SCROLL` 输出实际工作量、计时环境和墙钟统计。未跟踪的 `.codex-run/takeaway-before-1f3d3cf/` 保留旧源码快照；`.codex-run/takeaway-final-before.log`、`takeaway-final-after.log` 与 `takeaway-core-before.json` / `takeaway-core-after.json` 保留本次原始对照。

**生产环境 8ms 目标尚未验收。** 本轮已经证明重复挂载与框架更新被消除，仍需用相同尺寸、输入速度和图片状态的 Profile 构建采集 UI / Raster P50、P95 与长帧。首次图片下载、解码、GPU 绘制及真实屏幕呈现均不在本次墙钟测试的结论内。示例已有「帧耗时记录 → 外卖商家列表」入口，区分首次和稳定滚动；采样时关闭性能浮层，并分别记录纵向快滚和横向菜单。

## 2026-11-07 换绑文字复测

此前的 Android Profile 轨迹里，16.071 ms 尖峰的 `LAYOUT` 为 13.001 ms，内层 `RecyclerView.bind` 占 9.330 ms，其中 3.971 ms 在 `BUILD`。另一帧的 `RecyclerView.prefetch` 占 4.975 ms。两条路径都计入当帧 UI 开销。

本轮将变化文字直接更新到已挂载的 `RenderParagraph`，保留字号、行高、字距、图片 URL、卡片和横向菜单。菜单换绑跳过静止菜单的同偏移 `jumpTo`，仍会结束上家店的滚动或按住活动。已复用的标题排版对象在 12 次换绑中身份相同，单卡少 27 个 Element。

Windows 无头 Debug，仍使用上面的真实外卖页面和固定输入。前后各独立运行三轮，每轮记录 12 次，前 2 次预热。下表取三轮 P50、P95 的各自中位数，单位为毫秒。

| 场景 | 基线 P50 / P95 | 本轮 P50 / P95 |
| --- | ---: | ---: |
| 单卡换绑，断网占位 | 14.572 / 20.147 | 12.221 / 16.780 |
| 单卡换绑，图片缓存命中 | 12.402 / 19.940 | 9.679 / 17.456 |
| 整页纵向滚动，每帧 480 px | 17.283 / 26.180 | 14.680 / 21.410 |
| 整页纵向滚动，每帧 1 px | 3.967 / 4.609 | 3.603 / 4.828 |

480 px 快滚三轮 P95 分别为 27.722、26.131、26.180 → 21.410、21.390、21.981 ms。末帧挂载 Element 为 1455 → 1374，图片数量均为 12。热图换绑的同步绑定 P50 从 0.248 ms 变成 0.486 ms，文字更新提前到了通知阶段，整次换绑与 pump 的 P50 仍降低约 22%。小幅滚动 P95 有波动。手机尚未连接，本轮数据只覆盖无头主机耗时，8 ms 真机尖峰目标待 Profile 复测。

## Android 录屏暴露的冷图路径

19:20 的录屏在快滑经过未访问商家时多次显示整屏餐品占位，UI 浮层也反复超过 8 ms。此前的无头测试分别模拟拒绝网络与已经解码，未覆盖真实滚动中的下载、等待和首次解码。原网络模式为每家店及每道餐品分配不同 URL，复用图片位置时仍要等待新 URL 对应的图片。

外卖示例现在默认一次解码 Web 示例的 1448 × 1086 食物图集，按菜系和菜品位置绘制图块。三种容器使用同一资源；菜单的「网络图片」可单独复现旧路径。快跳测试在 8.333 ms 间隔下检查实际画出的图块，覆盖切换商家和三种容器，并验证离线模式不生成网络图片 Widget。图集首次解码仍是异步的。

此页关闭 RecyclerView 的同步条目预取。旧 Android Profile 的 8 个 8 ms 以上 UI 帧中，有一帧额外执行了 4.975 ms 的预取；其余 7 帧的预取均小于 0.03 ms，可见卡片的换绑和布局仍是主要开销。菜单在餐品数变化时只更新横向列表的范围，保留菜单外框。新版本的真机帧耗时和呈现间隔需要单独复测。
