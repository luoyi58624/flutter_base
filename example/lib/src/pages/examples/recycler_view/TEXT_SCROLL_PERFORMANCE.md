# 纯文本滚动的重复工作与快速滚动退化

日期：2026-11-06。用户先提供了约 17 秒的录像，前半段为 RecyclerView，随后切到官方 ListView。代表帧中的 UI 均值分别约为 1.1ms 与 0.6ms；两段手势并非严格同步的 A/B，不能据此推导完整帧分布、呈现间隔或输入延迟。

## 诊断

在 Windows 无头 Debug 中直接挂载真实 `RecyclerTextPage`，两种模式各预备 4 帧，再以每帧 3px 连续移动 24 帧。通过本次测试进程自己的 VM Service 读取 Dart Timeline，同时统计框架实际重建通知；没有连接或控制用户运行中的应用。

旧 `_obtainAndLayout` 对每个驻留条目都进入 `buildScope`、`updateChild` 检查、计时和 `RecyclerView.bind` 区间，即使该条目没有重新绑定且宿主描述完全相同。原来的正文 build/layout/paint 计数测试能证明正文没有重建，却看不到这层额外调度开销。轻量文字的实际工作很少，这部分固定成本更突出。

## 修改

- 仅在首次挂载、真正换绑或可见性变化时更新宿主并进入构建作用域；需要绑定时仍同步完成通知产生的后代重建。
- 稳定条目保留正常的 `RenderBox.layout` 检查，让正文自行变脏和变高仍能更新。
- 已有实测高度未变时直接返回，避免重复访问类型估高表。
- 独立标记可见性更新，避免将未绑定的宿主变化记为业务绑定。

没有给纯文本示例加固定行高，也没有更改两种容器的正文或减少可见内容。

| 同一 24 帧诊断 | 修改前 | 修改后 |
| --- | ---: | ---: |
| RecyclerView.layout 区间 | 24 | 24 |
| RecyclerView.bind 区间 | 1068 | 0 |
| 新建并挂载条目 | 4 | 4 |
| 真实纯文本行重建通知 | 4 | 4 |
| 测试查找器中的文本行数 | 45 | 45 |

这里的 1068 是旧的更新通道次数，不能称作 1068 次 Adapter 数据写入或 1068 次正文重建。官方 ListView 在相同测试中也仅新增少量条目，查找到的文本行数同为 45。

## Windows 快速滚动的另一个问题

用户随后提供 `QQ20261106-031822.mp4`，并明确说明运行于 Windows，对照容器是 **ElScrollView**。代表帧中 RecyclerView 的 UI 均值约 16ms，ElScrollView 约 6ms，两者 Raster 均在 3ms 左右；用户观察到的部分条件下耗时差超过三倍。录像有 Debug 标记，浮层均值也不是完整采样，不能把这些数值当作 Profile 性能比例。

这次以真实文本页、400×622 逻辑尺寸、相同字体和正文做短程诊断。控制器每帧直接移动 960px，连续 8 帧，绕过两者共用的鼠标平滑算法；没有采集或比较无头测试的毫秒数。

| RecyclerView 的同一快速滚动输入 | 默认每类型池容量 5 | 临时扩大到 64 |
| --- | ---: | ---: |
| 新建 holder | 226 | 2 |
| 真正换绑已有 holder | 46 | 264 |
| TickerMode 构建通知 | 525 | 517 |
| ExcludeFocus 构建通知 | 525 | 517 |
| 查找器中的文本行数 | 32 | 32 |

这些是 `fast-work-el.log` 中该次运行的工作量，不是稳定耗时门槛；预取仍开启且受本机实时预算影响，其他运行次数可能略有变化。同轮每帧只移动 3px 时，8 帧只新建 1 个 holder；移动 240px 时已新建 65 个。

原因已由源码和对照确认：`_layoutLinear` 先批量退出旧窗口，`_retire` 立即隐藏条目、更新 TickerMode/ExcludeFocus，再经小容量位置缓存进入类型池。类型池默认容量为 5，满后直接卸载；之后进入新窗口时，刚刚被卸载的同类型结构已无法复用，只能重新创建。滚动越快，同帧退出条目越多，越容易碰到这条路径。上一处跳过稳定条目空更新的修改不会解决它。

扩大池容量这里只用于验证创建抖动来源，并未修改示例默认配置。扩大后每行隐藏再显示的包装更新仍然存在，不能据此宣称耗时已经追平。ElScrollView 的本示例按窗口差量挂卸，行上只有无 RenderObject 的 `_ScrollItemScope`，该次 8 帧记录也没有逐行 TickerMode 或 Focus 的构建通知；两者的条目管理成本不同。

后续优化应评估本轮布局内暂存和优先复用离屏结构，布局结束后再把真正剩余的条目交给有容量限制的长期池，并避免立即复用条目的隐藏/显示往返。须保留真正离屏条目的停表和焦点排除语义；本轮尚未实施这部分，也未将容量 64 当作修复。

本机忽略目录 `.codex-run/recycler-video-031822/` 保存第二段录像抽帧、短程脚本及日志。本轮确认移除了稳定条目的空工作并定位快速滚动的额外退化，尚未采集修改后的 Windows 或 Android Profile 数据，不能宣称已经达到官方 ListView 或 ElScrollView 的帧耗时水平。
